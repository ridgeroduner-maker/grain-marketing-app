## 3. Findings, ranked

### HIGH

**F-01. Daily refresh has been failing since Nov 3; the live site is stuck on Oct 30 prices (11 days old).** [verified]
- Evidence: `gh run list`: 12 scheduled runs failed (2026-11-03 03:54Z through 2026-11-10 09:39Z, all UTC). Log: `ValueError: report 3049: no 'Grain Report for MM/DD/YYYY' line` for all 6 reports. USDA now prints `11/9/2026`, but `ingest/parse_pdf.py:76-80` on `main` requires two digits: `(\d\d)/(\d\d)/(\d{4})`. Live `meta.json`: `latest_report_date 2026-10-30`, `generated_at 2026-10-31T03:22:11-05:00`. Live site `Last-Modified: Sat, 31 Oct 2026 08:22:25 GMT`.
- Fix exists: PR #2, `parse_pdf.py:77-80` on the branch, `(\d{1,2})` and `int(...):02d`. Verified here against today's live PDFs (see section 2). Not merged; needs Ridge's typed APPROVE.
- Side note: PR #1 (`fix/single-digit-report-date`, a duplicate of the same fix) was closed on Nov 8 by an automation, not by Ridge. The branch still exists on origin.
- After merge: the push to `main` triggers "Publish to GitHub Pages". I expect it to pass the row-count guard (live baseline 66 rows, new export 67 rows, guard trips below 70%), but that is **[unverified]** until it runs.

**F-02. The 7-day stale limit is not enforced in the browser, so 11-day-old bids are still pinned and listed.** [verified]
- Evidence: `STALE_EXPIRE_DAYS = 7` (`ingest/config.py:81`) is applied only inside `export_json.export()` (drops rows older than 7 days). `ingest.py:115-116` skips the export entirely when any report fails (by design, "fail safe"). So when ingest fails for more than 7 days, the old file stays up unchanged. No JS file reads `stale_expire_days`. Live DOM now: 17 corn rows in the table, each tagged "7d old"; the Best-bid tab lists many corn bids as "not ranked ... 7 business days old". The report date of every row is 2026-10-30, which is 11 calendar days old.
- Mitigations already in place: red "Do not rely" banner, "Nd old" tags, nothing ranked, alerts silent. Residual risk: a farmer can still read and pin an 11-day-old price.
- Rule as stated by Ridge ("3 or more is hidden or unranked", ">7 days is past the stale limit") is only half met: unranked yes, hidden no.

**F-03. DRAFT legal pages with 8 unresolved placeholders are live on a public site.** [verified, known and pending]
- Evidence: `public/terms.html` has 5 `[[...]]` placeholder spans and `public/privacy.html` has 3; the live `terms.html` serves the same 5. Both pages carry a red "DRAFT - not legal advice, have a lawyer review" banner (`terms.html:19`, `privacy.html:19`). Open items include CME Group permission for futures settlements, acceptable-use wording, liability cap enforceability, venue, GitHub log visibility, children's privacy.
- Not a code bug. Listed High because it is public-facing legal exposure. Needs Ridge's decision (lawyer, or remove futures dollars via `FUTURES_DISPLAY: 'basis_only'` in `public/config.js`, which the app already supports).

### MEDIUM

**F-04. All-or-nothing ingest: one bad report blocks all six reports and also blocks code deploys.** [verified by log, design]
- Evidence: `ingest.py:107-125` counts failures and, with `--export`, refuses to export if any report failed; the workflow step then fails and `deploy` never starts. The same `build` job runs on every push to `main`, so a code-only change cannot ship while any one USDA report is unparseable. The app already supports per-report staleness (`app.js:88-91`), so a partial publish (the 5 good reports plus the failed report's old rows flagged stale) is something the front end could show.

**F-05. Nobody is alerted when the refresh fails.** [verified]
- Evidence: 12 failed runs over 8 days; the workflow has no notification step and creates no issue. The only warning is the in-app banner, which a farmer sees, not the owner. Whether GitHub's default failed-workflow email reached Ridge is **[unverified]** (cannot see his mailbox settings).

**F-06. History for Nov 2 to Nov 6 cannot be recovered by the daily job.** [code-read]
- Evidence: `config.py:25` `PDF_URL = https://www.ams.usda.gov/mnreports/ams_{slug}.pdf` serves only the latest edition; the keyless USDA metadata call returns only the latest report (checked: `listPublishedReport/3186` returned the 11/9 edition only). The 5 business days missed (Nov 2, 3, 4, 5, 6) will be gaps in the History chart and in "change since previous report" unless backfilled with `python3 -m ingest.ingest --source mars --backfill-days N`, which needs the free USDA API key. The MARS code (`ingest/mars_api.py`) has never run against the live API (see F-19).

**F-07. Alerts and chart history are keyed on SQLite row ids that are not stable if the history database is rebuilt.** [code-read; real-world impact unverified]
- Evidence: alert location is stored as `locKey = String(r.location_id)` (`app.js:350, 357, 388`); `history.json` and `latest.json` keys are built from `location_id`. The id is an autoincrement in `data/grain.db`, which lives only in the Actions cache (`pages.yml:68-77`; cache currently holds one 17 KiB entry). The workflow comment itself says the next run "starts a fresh history" if the cache is lost. A fresh database can number locations in a different order, so a saved "Aberdeen bid >= $4" alert could silently point at another place. Not reproduced.

**F-08. A bid row with a blank "Price Change" cell is silently dropped by the parser.** [verified, latent for in-scope crops]
- Evidence: `parse_pdf.py:49-53` `ROW_TAIL` requires a change token (`UNCH`, `UP x`, `DN x`). Real example in today's report 2887: `Flagler, CO  Bid  17.00  [blank]  17.00  6.50  DLVD-T  Current` (White Millet, out of scope) is not parsed and is not counted anywhere. A synthetic sunflower row with a blank change cell is dropped too (tested: 2 rows in, 1 out). The only safety net is the 70% row-count guard (`config.py:16`), which will not catch one or two lost rows.

**F-09. No CI on pull requests.** [verified]
- Evidence: `pages.yml:12-27` triggers are `push` to `main`, `schedule`, `workflow_dispatch` only. PR #2 shows `statusCheckRollup: []`. Tests run first inside the publish job (`pages.yml:62-66`), so a bad merge is caught only after it lands on `main`, and then it blocks the daily refresh until fixed.

### LOW

**F-10. Scheduled runs start hours late.** [verified from run history] The 23:07 UTC cron never started within an hour of schedule in 17 scheduled runs; those runs started 08:21 to 09:39 UTC (about 3 to 4 am Central), 9 to 10 hours late. The 02:07 UTC cron started 02:16 to 04:35 UTC. Net effect: USDA posts at about 2 to 4 pm Central and the site updates between about 9 pm and 4 am Central, not "after 4 pm". GitHub documents that scheduled runs can be delayed under load.

**F-11. Export computes "today" in UTC, the front end in Central.** [code-read] `export_json.py:98` uses `datetime.date.today()` on the UTC runner. The 02:xx UTC run happens on the previous Central evening, so `age_days`, `stale_days`, `meta.export_today` and the 7-day expiry are one day ahead for that run. The front end ignores `age_days` and uses its own Central business-day math, so user-visible effect is small; the 7-day cut-off is effectively 6 days on evening runs. `deploy/ci_check.py:central_today()` already does this correctly.

**F-12. No Content-Security-Policy is deployed.** [verified] The README recommends a strict CSP and says it was tested, but `index.html` has no CSP meta tag (only `referrer: no-referrer`) and GitHub Pages cannot set headers. The page uses `innerHTML` in 16 places with an `esc()` helper (escapes `& < > "`); the data is USDA text. No exploit found; this is defense in depth. A `<meta http-equiv="Content-Security-Policy">` with the README's policy would work on Pages (frame-ancestors is the only directive a meta tag cannot carry).

**F-13. Repo security features are off and `main` is unprotected.** [verified read-only via API] `secret_scanning`, `secret_scanning_push_protection`, `dependabot_security_updates` all "disabled"; `main` returns "Branch not protected". Pushing to `main` publishes the live site. These are free on public repos. **Not changed** (settings are Ridge's call).

**F-14. A background-sync alert can fire again when the app is next opened.** [code-read, unverified at runtime] `sw.js:49-52` records `lastFiredDate` only in IndexedDB; the page reads alerts from `localStorage` (`app.js:339`) and overwrites IndexedDB at start-up (`app.js:394`). So the page does not know the service worker already notified. Same notification `tag`, so it replaces rather than stacks.

**F-15. "7d old" tag means 7 business days.** [verified] `app.js:130` prints `${r.bage}d old`; live rows are 11 calendar days old. Confusing next to the banner's "7 business days".

**F-16. CI data gate rejects data older than 5 calendar days, even for a code-only deploy.** [code-read] `deploy/ci_check.py:19` `max_age_days=5`. A long holiday gap with no USDA edition would block any deploy. Holidays are not modelled in the business-day math either (`alerts-core.js`, `app.js`, `export_json.business_days_between`), so a Friday after Thanksgiving may show "Do not rely".

**F-17. Accessibility gaps.** [contrast computed; rest code-read] (a) White text on the primary buttons (`#4c8a2f`) is 4.21:1, under 4.5:1. (b) The header "Install app" button (dark text on a translucent white over green, about `#597d4c`) is about 3.4:1. (c) Muted 12px text on the directory panel is 4.45:1. (d) `index.html:105` `<canvas id="histChart">` has no text alternative or data table. (e) Alert "Delete" buttons have the same name for every alert (`app.js:359`). (f) The grey directory diamond is 2.99:1 against the page background, but has a darker ring. Not tested with a screen reader.

**F-18. Stale comments and docs.** [verified] `pages.yml:3-8` still says "PREPARED AS A FILE ONLY - NOT ACTIVE" (it is active); README says "Nothing is deployed yet" (README line 119) and elsewhere that the launch is pending; `docs/pages.yml.txt` is a duplicate copy of the workflow (identical today, a drift risk).

**F-19. The MARS API path is untested.** [verified] `ingest/mars_api.py:4` says it is covered by `tests/test_mars_normalize.py`, which does not exist. The module has never been called against the live API (no key). Needed for backfill (F-06).

**F-20. Latent: "Offer"/"Trade" rows are not filtered and would collide with "Bid" rows.** [code-read; none exist in today's six reports, checked] `ROW_HEAD` accepts `Bid|Offer|Trade`; the `bids` unique key (`db.py:34`) has no sale type; the export does not filter on it. If USDA ever prints an Offer line for the same place and delivery, it would overwrite the bid and be shown as a bid.

**F-21. Scheduled workflows are auto-disabled after 60 days without repo activity.** [documented GitHub behaviour for public repos, as quoted in `/workspace/optin-bids-plan.md` section 1.1; not observed] Low while the repo is active; a quiet winter could switch the refresh off silently (see F-05).

## 4. What is working well

- Fail-safe design held: the old data stayed up and the banner told users not to rely on it. No bad data was ever published.
- Parser is strict: it raises on layout change instead of guessing (this is also why F-01 was loud).
- No secrets, no tracking, no third-party requests by default; actions pinned to SHAs; least-privilege workflow permissions.
- Directory layer is cleanly isolated and correctly worded.
- Test suite is broad (115 to 118 tests) and runs in under 4 seconds.
