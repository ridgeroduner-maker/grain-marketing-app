# Grain Bids — first working version (LOCAL ONLY)

Public-facing PWA showing USDA's regional cash grain bids (posted about 2 to 4 pm Central each business day) (corn, spring wheat, winter wheat, soybeans, sunflowers)
within **300 miles of Gann Valley, SD** (44.0, −98.9), from **USDA AMS Market News only**. No profit calculator.
Nothing here is deployed, published or scheduled (a GitHub Pages workflow exists as a file only, see **Launch checklist**); work lives on branch `build/v1` (not merged to main). Everything is free/open-source.

## Run it

```bash
cd grain-app                     # needs: python3 (stdlib only) + pdftotext (poppler-utils)
./run_ingest.sh                  # fetch today's AMS reports -> data/grain.db -> public/data/*.json   (no API key needed)
python3 -m ingest.make_sample    # optional: SYNTHETIC 45-day history -> public/data-sample/ (git-ignored; only usable if ALLOW_SAMPLE is true in public/config.js)
./serve.sh                       # http://127.0.0.1:8765   (#history #best #alerts open a tab; ?sample=1 only works if ALLOW_SAMPLE is true)
python3 -m unittest discover -s ingest/tests && node public/alerts-core.test.js   # tests (116 python + 3 node scripts below)
node public/mapmode.test.js      # map-mode/config/service-worker guard tests
node public/directory.test.js    # Directory layer helpers (popup wording, links, fan-out); also run by the Python suite
python3 -m ingest.build_directory   # rebuild public/data/directory.json from data/elevator-directory.csv (build_dist.sh does this)
```

## Data freshness and failure behaviour (Reviewer round 1)
* Staleness is measured against **today (Central)**, not the newest date in the data: every row has `age_days`; the page shows a status banner with the newest report date, **Final vs Preliminary**, the **last successful ingest time**, and a red warning when the newest report is 2+ business days old. Rows 2+ business days old also get a "Nd old" tag; alerts ignore them.
* Rows from a region/report line that is **missing from that report's newest edition are not exported** (history keeps them), and rows older than 7 days (`STALE_EXPIRE_DAYS`) are expired. Both are listed in `meta.dropped_rows`.
* If **any** report fails to fetch/parse (or an in-scope report parses to zero bids) the ingest run is recorded `ok=0`, exits non-zero, and **does not export**; `public/data/` keeps the last good copy and the banner shows its age.
* Service worker caches **only 200 same-origin responses** (never 404/500 pages); app files and data are network-first; a saved copy served offline is flagged so the page says "offline — data generated N days ago".
* The Iowa "Mills and Processors" soybean row has **no region text in USDA's PDF**, so it can't be placed. It is now stored (`skipped_rows`), logged by the ingest, exported in `meta.skipped_rows` and listed under the table ("cannot be placed on the map"), not dropped silently.

## Best bid, labels and approximation
* Product choices are `grade · (protein) · freight`: **grades never merge** (ND soybeans US #2 FOB-T vs US #1 DLVD-T elsewhere stay separate; ND "Milling HRS" vs "HRS" separate) and delivered vs FOB are separate. Each bid shows its USDA **range**; ranking uses the top of the range (labelled as the app's reading); distance is shown on every ranked line and always labelled **straight-line miles**; sort by highest bid or closest.
* Region bids (everything except sunflowers) are drawn at an **approximate centre this app chose**: dashed pins with "~", legend, "approximate" popups, and a note that the 300-mile cutoff is approximate for them. Only sunflower processors are called town-level (`precision: town`).
* Basis is labelled with its exchange and month (e.g. "-90 to -80¢ vs CBOT Dec futures"; when USDA prints a different month at each end of the range, e.g. `-106F to -70X`, both are shown: "-106¢ vs CBOT Jan futures to -70¢ vs CBOT Nov futures"): CBOT corn/soybeans, MGE spring wheat, KCBT winter wheat — Data Scout's inference, arithmetic-checked by Reviewer; labelled as the app's reading in the footer.
* Wording: "posted about 2 to 4 pm Central", a USDA voluntary-reporting disclaimer (paraphrased, with a pointer to USDA's wording), and a footer list of what the app itself calculates (high-of-range, ranking, distances, pin positions, cents-to-dollar conversion, exchange named on basis, change since previous report).
* Leaflet (BSD-2-Clause, used only for the no-tile/dev fallback map) and Chart.js (MIT) license texts are in `public/vendor/` and linked from the footer.

## Map (Job 6: free, no account, no key, no billing)
Ridge declined Google billing, so Google Maps is **removed** (code, config, CSP, README steps, tests). The map is now **self-hosted Protomaps vector tiles (OpenStreetMap data) drawn in Leaflet**, served as one static file from the same site.

**How it works.** `public/mapmode.js` reads the single setting `MAP_TILES_URL` and picks `pmtiles` (default), `xyz` (raster provider), `osm-dev` (localhost only, URL empty) or `blank`. For `pmtiles`, the page first reads the first 1 KB of the file with a `Range` request and checks for a `206` and the `PMTiles` magic bytes; then it loads the vendored `protomaps-leaflet` and adds the layer to the same Leaflet map that holds the pins, the 300-mile ring and the dashed "~" region pins. If the file is missing, the host ignores Range (answers 200), the script fails, or an XYZ provider fails 4 tiles in a row with none loaded, the page switches to the **plain map with a notice** that names the cause. Nothing is requested from any other company in the default setup.

**What Ridge must do (one time, free, no account):**
1. Get the `pmtiles` command-line tool (one file, BSD-3-Clause): <https://github.com/protomaps/go-pmtiles/releases>; put it on PATH.
2. Run `./build_tiles.sh`. It finds the newest daily Protomaps build and extracts a box of about 350 mi around Gann Valley (bbox `-106.04,38.96,-91.94,49.10`, zoom 0 to 9) into `public/tiles/plains.pmtiles` (**about 17 MB**, 4 to 8 s here). The file is git-ignored on purpose; rebuild it now and then (roads and towns change slowly) by running the script again.
3. `./serve.sh` to look at it locally, then `./build_dist.sh` (copies the file into `dist/tiles/`).
4. Host `dist/` on a static host that answers HTTP **Range** requests with **206**. See hosting below. **GitHub Pages is the safest free pick.** Nothing was deployed by this build.
Optional: `MAXZOOM=10 ./build_tiles.sh` (about 38 MB, sharper; set `PMTILES_DATA_MAX_ZOOM` and `MAP_TILES_MAX_ZOOM` in `config.js` to 10 and 11).

**Why this option (read 2026-10-27).**
* It needs **no account, key, card, quota or third party at runtime**; the file is yours, so there is no terms change, outage or rate limit to depend on, and nobody else learns where a farmer looked.
* [OpenFreeMap](https://openfreemap.org/) is the runner-up (also no account/key): its [home page](https://openfreemap.org/) says "Using our public instance is completely free: there are no limits on the number of map views or requests. There's no registration, no user database, no API keys, and no cookies. We aim to cover the running costs of our public instance through donations." But its [terms](https://openfreemap.org/tos/) say "THE SITE IS PROVIDED “AS-IS,” “AS AVAILABLE,” AND “WITH ALL FAULTS.” WE MAKE NO WARRANTIES REGARDING ACCURACY, AVAILABILITY…", "We aim to maintain the Site’s availability but may discontinue it at any time without notice", and "We may use Cloudflare as a CDN… By using the Site, you consent to Cloudflare’s processing of your requests." A public app would depend on a donation-funded service with no SLA, and its vector tiles need MapLibre GL (WebGL, a much bigger library than Leaflet's plugin). Not chosen; easy to add later as one more provider.

Add its host to the CSP `img-src`.

**Recommended CSP when hosting** (tested here on the map page with the default setup: map tiles, pins and ring rendered and no console violations; a `<meta>` copy is not shipped in `index.html`, so add it as a response header or meta tag at your host): `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; worker-src 'self'; manifest-src 'self'; frame-src 'none'; object-src 'none'; base-uri 'self'; form-action 'self'`. Other tabs (History charts, alerts) were not run under this CSP.

**Caching.** `sw.js` (v7) ignores cross-origin requests and `.pmtiles` requests (a cached 200 copy would break range reads) and does not precache the tile file, so the map needs the network; offline you get the plain map with the notice. Tests assert both rules.

**Privacy**: with the default setup the map makes no third-party requests. A raster provider or `osm-dev` would see visitors' IP addresses and map areas.

## Directory layer (Job 11, branch `feature/directory`) - optional, OFF by default, NOT bids

A separate map layer of licensed grain buyers and warehouses from state lists: **names and towns only, no prices**. It is a *directory*, never a bid.
* **UI**: a separate checkbox under the map ("Directory only, NOT bids", off on every visit, nothing is stored), grey diamond markers (the bid pins are coloured circles and stay on top), a legend entry, a "Directory list" table with a find box and "Show on map" buttons (the keyboard / screen-reader route to every listing), and the reviewer's wording for the popup, footer attribution, correction line and "not for solicitation" line. `public/directory.js` owns all of it; the only edits in `app.js` are two lines that attach/detach the layer to the Leaflet map. Directory rows are **never** in `state.latest`, "best bid", the bid table, alerts or the service worker's alert check (static tests in `ingest/tests/test_directory.py` enforce that).
* **Popup**: name, town, state, category (only if the data has one), the list's agency and date, the approximate-location sentence, "Report a correction", and a "Company website (opens another site)" link **only when `bid_page_url` is set** (`target="_blank" rel="noopener noreferrer" referrerpolicy="no-referrer"`, plus a note that the outside site has its own cookies and tracking). All three pages also carry `<meta name="referrer" content="no-referrer">`, which is what makes the Privacy Policy sentence about not telling those sites which page you came from true.
* **Co-located points and clustering**: the data file carries display coordinates (`dlat`/`dlon`, from Data Scout's `lat_display`/`lon_display`: firms that share a town point are spread on a ~0.4 mi circle **for drawing only**; `lat`/`lon` and the distance `mi` stay the true values). The map draws each marker at `dlat`/`dlon`. If a row has no display coordinates (older CSVs) a deterministic pixel fan-out (rings of 16, 32... px, ordered by name then id) is the fallback. At **wide zoom (6 to 11)** nearby listings are grouped into numbered grey squares (fixed 48 px grid cells, so zooming in only ever splits a group; 827 listings = 98 groups at the default zoom 6, all single markers from zoom 12). Every listing is in exactly one group or marker (none hidden), a group square is a focusable button (`aria-label` "N directory listings (not bids) near Town, ST and nearby. Press Enter to zoom in."), Enter/Space/click zooms until it splits, and the "Directory list" table always lists every firm. Each single marker is a focusable button as before (`role=button`, `tabindex=0`, Enter/Space opens its popup). No library and no third-party request is used for any of this (`clusterRows` in `directory.js`, node-tested).
* **Data source (NOT in git)**: the compiled CSV from Data Scout (`elevator-directory-v2.csv`) is **never committed**: it carries per-row source notes (licence numbers, counties) and the repo is public. `.gitignore` excludes `data/source/` and `data/elevator-directory*.csv`; the working copy lives at `data/source/elevator-directory.csv` (or pass any path with `--csv`). Only the two lists "elevator/co-op" and "processor" in the **main** v2 file are used: the companion `...-nonelevators.csv` and `...-excluded.csv` files are never read. The committed artifact is just `public/data/directory.json` (`grain-directory-2`): per row `id, name, town, state, lat, lon, dlat, dlon, mi, category, src[], link, gq, fl[]` (no notes, licence numbers/classes, counties, crops or any other source column).
* **How to refresh the directory** (a local step, done by whoever has the CSV; nothing in the build or CI needs it): `python3 -m ingest.build_directory --csv /path/to/elevator-directory-v2.csv [--out public/data/directory.json] [--dropped-report /somewhere/outside/git/dropped.txt]`, then review `git diff public/data/directory.json`, run the tests and commit **only the JSON**. `./build_dist.sh` and `deploy/ci_check.py dist` never read the CSV: `build_dist.sh` runs `python3 -m ingest.build_directory --check` (schema `grain-directory-2`, count > 0, allowed fields only, every name has a business marker, safe links, known source keys, no notes/licence/county/email/phone text) on the committed JSON and fails if it is invalid. `LocalSourceFreshness` in the tests also compares the JSON with the local CSV when `data/source/elevator-directory.csv` exists (skipped in CI).

### Decision: the 17 MB map file (`public/tiles/plains.pmtiles`, 16,963,807 bytes)

### How the daily refresh works and why it fails safe
* **Schedule (cron is UTC and ignores daylight saving):** USDA posts about 2 to 4 pm Central (saved reports show 1:50 to 3:17 pm). Run 1 = `07 23 * * 1-5` UTC = 6:07 pm CDT / 5:07 pm CST. Run 2 = `07 2 * * 2-6` UTC = 9:07 pm CDT / 8:07 pm CST (the UTC date has rolled over, so Tue-Sat UTC is Mon-Fri evening Central); it catches a late USDA post or a failed first run. US daylight time ends **Nov 1, 2026**, so both runs sit one hour earlier on the clock after that and are still after 4 pm Central in both seasons. Minutes are not `:00` because GitHub can delay or drop top-of-hour runs. Holidays are not modelled (the run just republishes the latest report). GitHub also documents a `timezone: "America/Chicago"` key for schedules; I did not use it because I could not test it - Ridge may prefer it.
* **Steps:** tests (python + node) -> restore `data/grain.db` from the Actions cache -> use the live site's `latest.json` as the row-count baseline (falls back to the committed one on the first run) -> `python3 -m ingest.ingest --source pdf --export` (keyless) -> `deploy/ci_check.py data` (at least 30 rows, newest report date within 5 days, not sample data, required fields incl. the new low/high basis months) -> tiles -> `./build_dist.sh` -> `deploy/ci_check.py dist` (no `*.test.js`, no `data-sample`, `.nojekyll` present, data matches) -> official `upload-pages-artifact` (with `include-hidden-files: true`, otherwise `.nojekyll` would be dropped) -> separate `deploy` job (`deploy-pages`, `needs: build`).
* **Fail-safe:** `ingest` exits non-zero if any report fails to fetch/parse or the existing row-count guard trips (export does not run), and any failing step stops the job before `deploy` starts. The previous deployment stays live untouched, so **last good data stays**. The history cache is saved only when the whole job succeeds. A drop in rows is accepted only by a person: Run workflow > tick "accept_row_drop". GitHub emails the repo owner on failed scheduled runs by default (account notification settings; not checked).
* **Limits:** the price history lives in a cache, not git, so if the cache is evicted the history chart restarts from that day (prices unaffected). In a public repo GitHub disables scheduled workflows after 60 days without repository activity - re-enable under Actions or push any commit. Minimal permissions: workflow default `contents: read`; only the `deploy` job gets `pages: write` and `id-token: write`. No secrets are used.
